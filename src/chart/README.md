# Shared chart formats

`src/chart` owns application-wide serialized chart schemas and pure format conversion utilities.

- `garupa.ts`: canonical Garupa chart JSON schema. Besides BPM/SV/notes/Slide, it carries the chart header `{"type":"Header","data":"#HABAHIRO"}` (no beat, at most one; the original `#HABAHIRO` header) and the timed command `{"type":"System","beat":…,"data":"#LANE_CHANGE"}` (several allowed; as in the original converter the latest beat sets the change position; requires the HABAHIRO header). Notes wider than one lane, except Directional, require the HABAHIRO header. Bestdori V2 export drops both items.
  - Long. Garupa has no separate Long item: a Slide carrying `"long": true` is the original Long. The flag is only valid on the Long shape (exactly two nodes on one lane span, a Single/Skill head and a later Single/Skill/Flick tail, or a Directional tail that starts from the head's lane (`lane`) and may span several lanes toward its direction: the original Long multiple directional end; the simulator builds it as the Long root's Multiple after type with `LongMultipleDirectionalFlickAdd` members); without it every Slide, including a straight two-node one, is an original Slide. Bestdori V2 `Long` imports as such a flagged Slide and exports back to `Long`. The editor keeps the flag on its Slide chain and drops it on export once an edit leaves the Long shape.
  - Slide gesture nodes (extension). The original game only places flicks on a Slide's last node (Flick, Directional and Multiple-Directional tails). Garupa additionally allows a `Flick` or `Directional` connection as a Slide's head or an intermediate node. The simulator represents such a node with the original Slide tail kinds rather than a separate model: an intermediate node carries the original Slide end game type (flick end, directional end, or Multiple-Directional Add for width > 1), and a head records the same game type in `slideHeadGestureGameType`. The node's own gesture judgement follows the original flick-tail family: contact grace, origin, virtual perfect line, flick distance, contact span (a Directional of width > 1 tests its whole span, as the Multiple-Directional tail tests its group) and the touch-down cache (a touch-down on the node caches its result and timing; a later movement over the flick distance from the touch-down position judges the node with the cached result). A Directional of width > 1 also binds a touch-down anywhere over that span. A success judges as type 5/6/7 like the matching tail. This detection keeps its own origin, grace and cache, so the original tail state and tail cache keep running unchanged. Everything else follows the node's position in the chain exactly like a plain node at that position: movement and riding, timeouts and Miss (type 8, intermediate damage ÷5), a release before the last node (Miss type 8, after which the Slide continues), the lane light, sprite hiding and the tail-gesture block of a movement. Until it is judged the node shows its gesture, also after a touch-down: the original tail sprite (an intermediate Flick keeps the intermediate body `note_slide_among` under its flick icon) and its Add members, a touched-down head on the judge line with its flash. A judged gesture node is drawn as a plain node: an intermediate node as `note_slide_among` riding the line until it is passed, a head as the held body. A Directional of width w > 1 carries an exit offset of ±(w−1) lanes: once the node stops, the Slide line continues from the far end of the arrow, while the arrow sprite (and a head riding with it) stays at the line front minus the offset until the node is judged; it is then drawn at the front. Such a Slide stays on the original path; only inputs that the original geometry cannot carry (for example SV or non-lane positions) move it to the extension projection path.
  - Hidden Slide endpoints (extension). When a Slide's head is `Hidden`, its first visible node takes the head's role: before it is judged it registers a finger as a head does (any touch over it, without checking whether that finger already owns a note, so one finger may register several such Slides), and it is judged as an intermediate node. When a Slide's tail is `Hidden`, its last visible node is judged as an intermediate node and then handled as the tail: the finger is released and only the remaining geometry continues. `Hidden` nodes before the first or after the last visible node take no judgement and do not affect timeout windows.
- `bestdori-v2.ts`: canonical Bestdori V2 chart JSON schema used by import/export flows.
- `conversion.ts`: parsing, optional BPM-zero normalization, and Garupa ↔ Bestdori V2 conversion. Canonical optional `timingGroup` fields are omitted when absent/Global rather than emitted as own `undefined` properties; BPM-zero normalization preserves Slide owner groups.
- `index.ts`: the public module surface.

This module must stay independent from React, Tauri, simulator runtime types, skin resources, and editor controller state. `src/chartCore.ts` retains the editor's internal `ChartNote` model and editor/display-oriented operations; serialized format types do not belong there.

Chart metadata no longer embeds Data URLs or remote URLs. BGM, cover, MV and custom background are main-program `ResourceRef` values persisted separately in `chart-resources.v5.json`; portable Garupa/Bestdori chart schemas remain resource-independent. User and provider-downloaded chart media belong to the recoverable current-session workspace, while Builtin/default Skin refs remain application resources. The one-time v2/v3/v4 migration adopts provable bytes/refs into workspace records; an ambiguous identity leaves that migration action unavailable while preserving durable data and never substitutes a default.
